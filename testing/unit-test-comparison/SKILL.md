# Unit Test Comparison Skill

## How to Use

Invoke this skill by asking Copilot to evaluate a test generation run. You will need to provide:

1. **Two folders** — one containing the Testing Agent run artifacts, one containing the GH Copilot Agent Mode run artifacts
2. **The original source file** being tested (e.g., the `.cs` file under test)
3. **The LLM model used** for each run (auto-extracted from logs)

### Example prompts

```
Evaluate the test runs in C:\path\to\TestingAgentFolder and C:\path\to\CopilotFolder, source file is C:\path\to\MyClass.cs
```

```
Run a unit test evaluation comparing these two folders: <folder1> <folder2>
```

```
Assess the test quality from these runs: <folder1> and <folder2>
```

### What you get

Three markdown reports saved to a timestamped folder (`MMDDYYYY-UnitTest-Run<N>`):

| Report | Description |
|--------|-------------|
| `MMDDYYYY-TestingAgent-<Project>.md` | Detailed analysis of the Testing Agent run |
| `MMDDYYYY-GHCopilotAgent-<Project>.md` | Detailed analysis of the GH Copilot Agent Mode run |
| `MMDDYYYY-UnitTestEvaluation-<Project>.md` | Side-by-side comparison with test quality assessment and suggested issues |

### What each folder should contain

| Folder | Expected contents |
|--------|-------------------|
| Testing Agent folder | `codetestingagent.log` + any `.cs` test file(s) generated + `coverage.cobertura.xml` (if available). Log file is located at: `%TEMP%\VSCodeTestingAgentLogs` |
| Copilot folder | A log file (e.g., `Copilot log.txt` copy and paste from VS "GitHub Copilot" output window) + any `.cs` test file(s) generated + `coverage.cobertura.xml` (if available) |

> **Tip:** Use the `collect-test-testingagent-logs` skill to gather Testing Agent artifacts (TRX, console output, coverage, Copilot logs, and Testing Agent logs) into a timestamped folder. Use the `collect-test-copilot-logs` skill to gather Copilot artifacts. These skills ensure all required files are collected before running the evaluation.

---

## Purpose

Given a log file from a **Testing Agent** run and a log file from a **GH Copilot Agent Mode** run — both targeting the same source file with a "write unit tests" prompt — generate three evaluation reports:

1. **Testing Agent report** — detailed analysis of the Testing Agent log
2. **GH Copilot Agent Mode report** — detailed analysis of the GH Copilot Agent Mode log
3. **Comparison report** — side-by-side comparison of both runs

---

## Inputs

You will be provided:

- **Testing Agent folder** — a folder containing the Testing Agent run artifacts. Look for `codetestingagent.log` and any `.cs` test file(s) generated by the Testing Agent.
- **GH Copilot Agent Mode folder** — a separate folder containing the GH Copilot Agent Mode run artifacts. Look for a log file (e.g., `Copilot log.txt`, `Copilot log.log`) and any `.cs` test file(s) generated by Copilot.
- **File matching** — use the folder each file lives in to determine which run produced it (Testing Agent vs. Copilot). Do not rely on file names to distinguish runs. If one folder contains files not present in the other, ignore the extra files — only evaluate files that are common to both or relevant to that run's own report.
- **Model used** — auto-extract from the Testing Agent log (`model:` on the `Starting test generation with scope` line) or from the Copilot diagnostic log (`PreferredModelFamily=` in the config section). Only ask the user if neither source contains the model. Include in run metadata for both reports and in the comparison table.
- **Target source file** — the original `.cs` source file that was targeted for test generation. Ask the user for the file path. If not provided, extract the path from the log content (look for `#file:` mentions in the prompt or `Mapped source file` entries). Read this file to understand the actual API surface, branches, constructors, and logic — this is essential for accurate test quality classification and coverage gap analysis.
- **Output directory** — present the default location to the user and ask them to confirm or pick a different folder. Remember their choice for future runs of this skill.
  - **Default:** the same folder as the Testing Agent input folder
  - **Confirm:** "I'll save the reports to `<default path>`. Is that OK, or would you prefer a different location?"
  - **Remember:** If the user picks a custom location, store it and use it as the new default for subsequent runs. If they confirm the default, continue using it.

## Report 1: Testing Agent Report

### Required Sections

#### Header
```
# Testing Agent Evaluation — <ProjectName> (<MM/DD/YYYY>)
```

#### Context
- Why was this file recommended for test generation? (extract from any available context or note as "N/A")

#### Run Metadata
- **Tool:** .NET Testing Agent
- **Prompt:** the exact prompt passed to the Testing Agent (extract from log, e.g., `@test Write unit tests for all the open files`)
- **Target:** full path to the source file(s) or folder under test
- **Date/Time:** date and time of the run (extract from first timestamp in log)
- **Visual Studio Version:** auto-extract from the Copilot diagnostic log (`copilot-output.log`). Search the first 50 lines for `Copilot chat version`. The line format is: `Copilot chat version <CopilotVersion>. VS: <VSVersion>. Session: <id>`. Extract the value after `VS:`. If the Copilot log is not available, fall back to `run-metadata.md`. Only ask the user if neither source contains the VS version.
- **Copilot Chat Version:** auto-extract from the same log line — the value after `Copilot chat version` and before the first period (e.g., `18.5.38402+d52add363e`). Note "Unknown" if not found.
- **Agent version:** extract from first line of log (e.g., `.NET Code Testing Agent v0.4.943-alpha+...`)
- **Model:** auto-extract from the Testing Agent log (`model:` on the `Starting test generation with scope` line). If not found, extract from the Copilot diagnostic log (`PreferredModelFamily=`). Only ask the user if neither source contains the model.
- **Log file:** full path
- **Total duration:** calculate from first and last timestamps in the log (format: `X minutes Y seconds`)

#### Result
- One-line summary (e.g., "0 tests generated — compilation errors could not be resolved")

#### Code Coverage
- **Initial coverage:** percentage before test generation (extract from log)
- **Final coverage:** percentage after test generation (extract from log; note "N/A" if tests didn't compile/run)
- **Coverage change:** difference (e.g., `+15.2pp` or `No change`)

#### Coverage Artifact
- **Coverage file:** full path to `coverage.cobertura.xml` if provided, otherwise note "Not provided"
- **Notes:** mention whether the file was sourced from the Testing Agent artifacts folder

#### Timeline
- Use a table with `| Time | Event |` columns
- Extract key events from the log:
  - Agent start
  - Solution found
  - Run context created
  - Prompt analysis completed
  - Test project built
  - Initial test run results (existing test count, pass/fail, initial coverage %)
  - Test file mapping
  - LLM code generation start
  - Each LLM response (test count, duration)
  - Merge results
  - Test file creation
  - **Initial diagnostics (error count)** — bold if errors present
  - Fix iterations (range of timestamps, outcome)
  - Build and fix completion
  - Test execution results (success/fail, test count)
  - Final coverage
  - Agent completion / cancellation
  - Summary generation

#### Compilation Errors
- Table with `| Error Code | Description |` columns
- List each unique error code (CS1061, CS1729, CS1503, CS0103, etc.)
- Include a plain-English description of what went wrong
- If no compilation errors occurred, note "No compilation errors" and skip the table

#### Deleted Tests
During fix iterations, the agent may delete tests it cannot get to compile. Track these by comparing the initially generated test methods (visible in the log after LLM code generation) against the final test file.

- **Table format:**
  ```
  | Deleted Test Method | Reason (from log) | Could It Have Been Fixed? |
  ```
  - List each test method that appeared in the log's generated code but is absent from the final `.cs` file
  - Extract the reason from fix iteration log entries (e.g., "Removed due to CS1061", "Deleted after 3 fix attempts")
  - Assess whether the test could have been salvaged (e.g., "Yes — just needed the correct constructor overload" or "No — depends on missing InMemory package")
- If no tests were deleted, note "No tests were deleted during fix iterations" and skip the table
- **Important:** Deleted tests that tested meaningful behavior are high-value signals — they indicate the agent had the right testing intent but couldn't execute it. Flag these specifically for the Suggested Issues section.

#### Analysis
- Bullet points summarizing root causes of any issues
- Typically covers:
  - Missing NuGet packages
  - Wrong API assumptions (constructors, methods)
  - Type/namespace confusion
  - Fix loop effectiveness
  - Tests deleted during fix iterations (count and whether they were behavioral)
- If the run succeeded cleanly, summarize what went well instead

#### Test Quality Assessment
If the generated test file(s) are provided, read the actual test code and the target source file, then assess quality:

- **Test file(s):** list the path(s) to the generated test file(s)
- **Total test methods:** count of distinct test methods — detect the test framework in use and count accordingly:
  - **MSTest:** `[TestMethod]` methods (parameterized `[DataRow]` tests count as one method with N cases)
  - **xUnit:** `[Fact]` and `[Theory]` methods (parameterized `[InlineData]` tests count as one method with N cases)
  - **NUnit:** `[Test]` and `[TestCase]` methods (parameterized `[TestCase]` tests count as one method with N cases)
- **Test classification:** categorize each test method into one of:
  - **Behavioral** — tests meaningful logic, branching, side effects, or return values based on different inputs/states
  - **Trivial** — tests something with near-zero chance of failing (e.g., constructor creates non-null instance, constant return value called multiple times)
  - **Redundant** — duplicates the intent of another test without adding new coverage
- **Classification table:**
  ```
  | Test Method | Category | Notes |
  ```
  - List every test method with its category and a brief note on what it verifies
- **Quality summary:**
  - Count of Behavioral / Trivial / Redundant tests
  - Percentage of tests that are Behavioral
- **What's well done:** bullet points on strong testing practices observed (e.g., mock verification with `.Received()`, proper AAA pattern, edge case coverage, testing side effects)
- **What's missing:** bullet points on gaps (e.g., exception propagation tests, concurrency, null guard tests, state transition edge cases, integration with domain invariants)

## How to Extract Data from Logs

### Testing Agent Log
- **Timestamps:** Each line starts with an ISO 8601 timestamp (e.g., `2026-02-06T22:25:50.9399643Z`)
- **Duration:** Subtract first timestamp from last timestamp
- **Key patterns to search for:**
  - `Generated \d+ test` — test generation counts
  - `Errors for` — compilation errors
  - `CS\d{4}` — specific C# error codes
  - `Test execution completed` — test run results
  - `Test count` — final test counts
  - `Coverage` — coverage percentages
  - `cancel` — cancellation events
  - `fix cycle` / `Iteration` — fix loop iterations
  - `Mapped source file` — test file mapping
  - `merged` — merge results
  - `Successfully created test file` — file creation
  - `Removing test` / `Deleted` / `removed` — tests deleted during fix iterations (compare initial generated count vs. final count)

### GH Copilot Agent Mode Log
- **Timestamps:** Usually absent from individual lines; look for `Server time from HTTP Date header` entries
- **Key patterns to search for:**
  - `Begin sending message` — user messages
  - `Request content:` — prompt text
  - `SemanticSearchStrategy` — semantic search rounds
  - `FileEditingState` — file edits generated
  - `Error` / `Warning` — errors and warnings
  - `PLAN UPDATE` — plan tracking issues
  - `statusNotification` — auth/status errors
  - `MCP server` — MCP server availability

## Suggested Issues to Open for the Testing Agent

After completing the evaluation, review the results and suggest filing issues for the Testing Agent where applicable. Only suggest issues that are **concretely implementable** based on patterns observed across evaluations. Include this section at the end of the **Comparison report** when findings support them.

Generate up to **10 issues**, each specific to patterns observed in the current evaluation. Do not use pre-written or standing issues — every issue must be derived from evidence in the current run's logs, test code, or comparison findings.

### HIGH-ROI ISSUE PRIORITIZATION (Required)

When producing this section:

1) Assign an ROI tier to every issue:
   - ROI: HIGH
   - ROI: MEDIUM
   - ROI: LOW

2) Compute ROI using these criteria (use best judgment, no need to show the math):
   - Breadth (how many projects/users likely hit this): 0–3
   - Impact (time saved, correctness, reliability): 0–3
   - Fixability (clear repro + implementable heuristic): 0–2
   - Urgency (blocks runs, causes hangs/failures): 0–2
   - LLM waste (LLM calls, tokens, or time consumed by this issue relative to the run total): 0–2
     - 0 = N/A or negligible LLM cost (quality gap, no extra calls)
     - 1 = moderate LLM cost (< 30% of total run calls/tokens)
     - 2 = high LLM cost (≥ 30% of total run calls/tokens consumed by this issue)
   - Total: 0–12

   Map score to tier:
   - 9–12 => ROI: HIGH
   - 5–8  => ROI: MEDIUM
   - 0–4  => ROI: LOW

3) Sort the issues by ROI tier first (HIGH, then MEDIUM, then LOW).
   Within the same tier, sort by score descending.

4) Include the ROI tier in each issue header:
   Example: `

### Issue 1 (ROI: HIGH): 17 tests still failing at final run with no fix cycle triggered`

5) For each issue, include a short "Why ROI" line (1 sentence) stating the main reason:
   Examples:
   - "Why ROI: Prevents failing-test accumulation that wastes the entire generation run."
   - "Why ROI: Cuts large volumes of low-value tests across many typical C# codebases."

6) Do not change the substance of the issues — only add ROI labeling, sorting, and the brief "Why ROI" line.

### Issue Format

Each issue must follow this format:

```

### Issue N (ROI: <tier>): <Short title>

- **Problem:** <What was observed in this evaluation — cite specific test methods, error codes, or log entries>

- **Suggested fix:** <Concrete, implementable change the agent could make>

- **Fix location:** <Where the fix would be implemented — one or more of: `LLM prompt/model`, `Testing Agent orchestrator`, `Copilot Agent orchestrator`, `Roslyn analyzers`, `NuGet/MSBuild tooling`, `VS test runner`, `User workflow`>

- **LLM cost:** <Estimated LLM calls, tokens, and/or time consumed by this issue — derived from correlating log entries with the problem's fix iterations or time window. For Testing Agent issues, use `LLM call` / `TotalElapsed` patterns. For Copilot issues, use `EventType(9)` calls and `InputTokenCount`/`OutputTokenCount` entries. Format: `~N of M LLM calls (X%), ~T tokens, ~D elapsed` — include whichever data is available. If the issue did not consume extra LLM resources (e.g., a test quality gap), note "N/A — quality gap, no extra LLM cost". If LLM usage data is not available in the log, note "Unknown — LLM usage data not available in log".>

- **Why ROI:** <1 sentence — the main reason this issue merits its tier>
```

**Fix location values** — use the most specific label(s) that apply:
- **LLM prompt/model** — the fix requires better prompting, fine-tuning, or model capability (e.g., generating smarter test code)
- **Testing Agent orchestrator** — the fix is in the Testing Agent's control logic (e.g., fix loop, file selection, stall detection, strategy switching)
- **Copilot Agent orchestrator** — the fix is in Copilot's agent mode control logic (e.g., tool selection, file handling, validation loops)
- **Roslyn analyzers** — the fix involves static analysis, diagnostics, or code-aware checks (e.g., detecting sealed classes before generating mocks)
- **NuGet/MSBuild tooling** — the fix involves package management, build configuration, or project file handling
- **VS test runner** — the fix involves test discovery, execution, or caching in Visual Studio
- **User workflow** — the fix is a recommendation for the user (e.g., extracting an interface, changing project structure)

**Common patterns to look for (use only if evidenced):**
- Trivial / filler tests (e.g., constructor-not-null, constant return value re-tests)
- Not reusing existing test helpers / builders in the test project
- Missing negative mock verification (`DidNotReceive` / `Times.Never`)
- Exception propagation tests not generated (what happens when a dependency throws?)
- Cancellation token not tested for actual cancellation scenarios
- Tests that duplicate intent with different setup but same assertion
- Missing state transition edge cases (e.g., calling a method on an already-transitioned entity)
- Test naming inconsistencies or misleading test names
- Unnecessary test setup complexity (mocking things that aren't used in the test)
- Missing async edge cases (e.g., `Task.FromException`, `Task.FromCanceled`)
- Not testing all branches visible in the source (if/else, switch, null checks)
- Generated tests tightly coupled to implementation details rather than behavior
- Test file structure issues (e.g., all tests in one class vs. logical grouping)
- Missing NuGet package installation causing compilation failures
- Type or namespace confusion (e.g., two classes with the same name in different namespaces)

Only include issues that are **directly evidenced** by the current evaluation. If fewer than 10 issues are supported by the data, include only those that are.

## Scoring (Hybrid: Rubric + LLM Judge)
This skill computes a **rubric score (0–100)** for **both** the Testing Agent and GH Copilot Agent Mode runs, then applies a **bounded LLM adjustment (‑10 … +10)** to each.

### Rubric (0–100)
*A deterministic score built from hard signals extracted from the run—coverage deltas, compile status, fix‑loop outcomes, log events, and the resulting test classifications.*

Five dimensions (0–20 each):

| Dimension | 0–5 | 6–10 | 11–15 | 16–20 |
|-----------|-----|------|-------|-------|
| **Correctness** | No tests compile or run | Some tests compile but most fail | Most tests pass with minor issues | All tests pass, no compilation errors |
| **Coverage Impact** | No coverage change or decrease | <5pp coverage increase | 5–15pp coverage increase | >15pp coverage increase |
| **Behavioral Depth** | All tests trivial or redundant | <30% behavioral tests | 30–60% behavioral tests | >60% behavioral, edge cases covered |
| **Test Design Quality** | No AAA pattern, poor naming, no mocks | Inconsistent patterns, some mocks | Good AAA, proper mocks, minor gaps | Clean AAA, accurate mocks, negative cases |
| **Stability & Reliability** | Agent crashed or hung, no output | Multiple fix loops, tests deleted | Minor fix iterations, all tests kept | Clean run, no fix loops needed |

Inputs are derived from the log, coverage data, generated test files, and the Test Quality classification table.

Compute a separate rubric score for each run.

### LLM Adjustment (‑10 … +10)
*A bounded qualitative pass that captures nuance—assertion quality, branch‑aware behavior checks, negative‑path realism, and mock‑interaction accuracy—that raw metrics miss.*

A constrained LLM reviews qualitative aspects and proposes per‑dimension deltas in **[‑2..+2]**, each justified with citations to:
- test method names,
- log timestamps (ISO 8601), or
- classification notes.

If evidence is insufficient, the delta is 0. The LLM cannot change factual metrics.

Apply adjustments independently to each run's score.

### 🏆 Final Score
Formula used: `final = clamp(rubric + Σ(deltas), 0, 100)`

Display each final score prominently with a status emoji based on the score range:
- ✅ **80–100** — Strong test generation
- ⚠️ **50–79** — Partial success, notable gaps
- ❌ **0–49** — Significant issues, low-quality output

The **Comparison report** includes a scoring summary table:

```
| Scoring | Testing Agent | GH Copilot Agent Mode |
|---------|---------------|------------------------|
| Rubric score | X | X |
| LLM adjustment | ±X | ±X |
| **🏆 Final score** | **X/100 <emoji>** | **X/100 <emoji>** |
```

Each individual report displays the score prominently:
```
## 🏆 Final Score: <score>/100 <emoji>
Rubric: <rubric_score> | LLM Adjustment: <±delta>
```

Each individual report also includes:
- Final score, rubric score, and total LLM adjustment
- Per‑dimension breakdown
- Evidence‑linked rationale for any LLM deltas
